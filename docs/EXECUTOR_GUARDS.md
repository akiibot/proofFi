`app.execution.gate.claim_execution(engine, body, actor_id, *, policy, recheck=None)` accepts a server-derived actor, existing ExecuteRequest and trusted TestnetPolicy. The optional server-only recheck consumes TrustedSimulationInput, returning PolicyVerdict and SimulationRun. There is no successful default, public injection mechanism, environment flag or fallback. Farid's policy/simulation implementation must be connected by the lead in PF-029/PF-015; this branch does not implement those modules.

Inside SQLite BEGIN IMMEDIATE, the gate reloads the stored certificate, verifies Ed25519/hash/expiry, exact action/transaction and metadata, authoritative state/confirmed policy, stored candidate/config/simulation/verification, operational token/recipient/wallet/fee restrictions, and the matching human decision. It independently requires approval above the current autonomy limit and for unknown recipients. It reruns the trusted policy/simulation seam and compares deterministic evidence, checks probability thresholds and all four named stresses, and rechecks expiry after computation.

It reserves the certificate, idempotency key and chain/sender/nonce, consumes the approval and appends EXECUTION_CLAIMED atomically. Concurrent calls create one claim. Historical reservations require authentic signatures/hash/metadata even after expiry; retain old public verifier keys or execution fails closed. Signed certificate bytes stay unchanged; transaction hash remains null, status CLAIMED. SQLite serializes writers; unsupported database backends fail explicitly. The nonce lookup scans existing claim-bound certificates, appropriate to this single-wallet demo; it is not an indexed multi-wallet production design.

A durable claim is not signing authority that may be reused. PF-015 must preserve exact signed bytes and deterministic transaction hash before broadcast, prevent duplicate signing after process failures, recheck live chain nonce/token decimals/code/balances/gas/fees and state/policy at the signing boundary, and reconcile ambiguous outcomes without automatic re-signing. This branch does not claim that service-level at-most-once signing or chain ledger reconciliation has been implemented. Never delete a claim to retry.

Tests use migrated SQLite, real certificate cryptography, authenticated approval recording and concurrent threads. Test-only risk callbacks supply isolated fixture evidence. ## Internal signing slice (2026-10-16)

PF-029 merged through PR #61 at `97a319808510b0d09357a14b7302d22f179682d1`. The new internal `sign_authorized_once` boundary connects its real recomputation and read-only chain validation. Public `/execute` remains NOT_IMPLEMENTED. This section supersedes the earlier unconnected-boundary status; PF-014 remains open pending full executor integration.

The first SQLite transaction permanently claims authority and consumes any approval before invoking a signer. A second writer transaction reloads current authority and artifacts, validates the complete audit chain and exact claim/consumed-approval binding, recomputes risk, checks operational allowlists and fresh chain transaction fields, and rechecks certificate validity before signing. It independently decodes and recovers the actual EIP-1559 output, comparing every certified transaction field. The signed-event audit stores only a SHA-256 digest; it does not claim broadcast or an Ethereum transaction hash.

The private process-local result contains raw signed bytes, excluded from its representation. These bytes are not exposed by an API, written into the existing Execution payload, or broadcast. PF-015 must durably preserve exact bytes before sending and reconcile receipts/ambiguous sends. A failed signer, audit write, transaction commit or lost process result leaves the original durable claim reserved. No automatic re-signing or claim deletion is permitted. This conservative one-attempt boundary can strand an attempt; it does not provide crash recovery.

Tests use real SQLite, issuance, risk recomputation and EIP-1559 signatures with explicitly isolated financial configuration and a known test-only key. Only external RPC responses are substituted. No live-chain receipt, approved financial configuration or completed acceptance gate is established.
