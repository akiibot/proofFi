# Base Sepolia demo configuration checklist

Owner: lead. Tracks infrastructure for PF-004/PF-030/PF-015. Current status: no funded demo wallet, chosen token or approved recipient. Configuration alone does not enable POST /execute; trusted verification, approved policy and executor integration must land first.

1. Use a dedicated demo wallet for Base Sepolia, chain ID **84532**. Record its public lowercase address. Keep its private key only in the ignored local `.env` as `SIGNER_PRIVATE_KEY`; set `WALLET_ADDRESS` to the matching address. Do not reuse a wallet holding real assets.
2. Fund this wallet with Base Sepolia native test ETH for gas. Record the real funding transaction and confirm the native balance on the intended chain. A synthetic dollar balance in ProofFi does not fund the wallet.
3. Choose an actual deployed ERC-20 demo token on Base Sepolia, or deploy one through the team's reviewed test-token tooling. Set `TEST_TOKEN_ADDRESS` to its real lowercase contract address. Read deployed bytecode, `decimals()` and `balanceOf(wallet)` through RPC. Decimals must be 2..18 under the existing contract. Acquire enough test tokens for the intended transfers. Example addresses in contract fixtures are not deployed tokens.
4. Select a demo recipient controlled by the team. Set its lowercase address as `APPROVED_RECIPIENT`; independently confirm it. Confirmation belongs in the explicit Constitution flow when PF-006 lands; setting environment values must never silently activate a policy.
5. Set `RPC_URL` locally to a Base Sepolia HTTP RPC. Keep any provider credential private. Read `eth_chainId` and require 84532; do not trust the URL's name. Inspect the pending wallet nonce, native balance, token code, decimals and token balance before issuing a certificate.
6. Generate a dedicated Ed25519 verifier key locally. `VERIFIER_PRIVATE_KEY` is a reserved backend-only setting; PF-029 must define and validate its runtime loading format before use. PF-012's implemented verification keyring accepts `VERIFIER_PUBLIC_KEYS_JSON` mapping a chosen key ID to 32-byte Ed25519 public-key hex. No test key may become a runtime key. Never paste private material into chat, issue bodies, logs, browser fields or frontend environment variables.
7. Record operational gas-limit and max-fee ceilings with their units, plus the explicit synthetic fee assumption for the risk model. The signer already accepts these through trusted TestnetPolicy; no environment loader for these ceilings or token decimals is wired yet. PF-015 must construct and validate that policy from trusted configuration and live reads. Do not invent variable names and assume they are active.
8. Once dependencies are reviewed/merged, independently verify the exact action, obtain any required human approval, execute once, and record the genuine returned transaction hash, receipt/block/confirmations and audit linkage. A receipt fixture or a computed hash without broadcast/confirmation does not satisfy the live demonstration.

Public handoff values to record (currently all unset): wallet address; token address; decimals; approved recipient; actual native/token balances and observation time; funding transaction reference; gas/fee ceilings. RPC credentials, signer private key, verifier private key and LLM key remain local. An LLM key is only needed when the live planner integration is ready; the planner never receives execution secrets.

The literal financial fixture remains $12,000 assets minus $7,000 tuition, $2,000 reserve and $3,200 living expenses = **−$200 before shocks/fees**. On 2026-10-15 the lead delegated the interim choice; we preserve these figures and add no invented income or probabilities. The policy/optimizer must report NO_SAFE_ACTION when the real checks find no safe allocation. Positive Scenario A and reduced positive Scenario C still require an explicitly approved income/assumption set later.
