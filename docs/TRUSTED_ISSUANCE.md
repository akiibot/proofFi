# Trusted certificate issuance (PF-029)

`POST /verify` consumes the existing `ActionRequest` only. Authenticated session and CSRF checks still apply. A planner's reason is untrusted text; a client cannot supply state, policy, config, verdict, simulation, transaction, key or approval authority.

The trusted service holds a SQLite `BEGIN IMMEDIATE` writer transaction, reloads the actor's current financial snapshot and confirmed Constitution, and requires exactly one explicitly selected trusted simulation-config record under the current PF-009 selection convention. It validates metadata/digests and recomputes real simulation paths, metrics, all four named stresses and every policy check. A failed named stress adds a `named_stresses` failure to the existing verdict format. Any hard failure yields DENY with no certificate, regardless of an approval requirement or planner text. Denial persists candidate/simulation/verification and linked rejection audit evidence; it needs no RPC or signing key.

For a compliant action, read-only Base Sepolia RPC checks require chain 84532, deployed token code, matching decimals, sufficient token and native gas balances, pending wallet nonce, current base fee within the explicit fee ceiling and gas estimate within the explicit gas limit. Exact ERC-20 bytes and integer cent-to-base-unit mapping use the existing ChainTransaction model. The service never imports or invokes a transaction signer, asks RPC to sign, or broadcasts. RPC observations do not reserve the wallet nonce and are not a receipt. RPC provider retries are disabled and each request has a five-second timeout.

Only then does the service create a five-minute Ed25519-signed certificate, using the existing canonical payload, hash and signature encoding. A random certificate nonce, exact state/policy/config/evidence, action digest, transaction and approval requirement are bound. It checks its signature/time against the trusted public keyring and atomically persists linked verification, certificate and audit records. A missing dependency, corrupt stored artifact/audit chain, ambiguous config, key mismatch, RPC failure or write failure rolls back all new artifacts. Existing simulation identity is reused only after complete recomputation and audit binding validation; existing action IDs cannot be rebound to different state or bytes. Repeating a successful verification may issue a new certificate, but does not create an approval or execute anything. PF-014's independent claim guard must still refuse reuse of a wallet nonce.

## Explicit backend configuration

All values remain unset in the checked-in environment example. No test configuration or key is selected for normal runtime.

- `VERIFIER_PRIVATE_KEY`: exactly 64 lowercase hex characters encoding a 32-byte Ed25519 private seed. This is a dedicated certificate key, separate from `SIGNER_PRIVATE_KEY` (the executor's EVM key). No automatic key generation or fallback.
- `VERIFIER_KEY_ID`: a nonempty existing contract identifier, at most 100 characters.
- `VERIFIER_PUBLIC_KEYS_JSON`: environment JSON object mapping key IDs to 32-byte public-key hex, consumed by the existing PF-012 keyring loader. The current private key must match its named public key. Retain historical public keys. For API-alone startup, explicitly supply this process environment variable; `npm run dev` loads root `.env` into the process environment. Never paste a private seed into chat, GitHub or browser inputs.
- `RPC_URL`: an explicitly configured HTTP(S) Base Sepolia RPC endpoint. Keep provider credentials backend-only.
- `VERIFIER_TRANSACTION_CONFIG_JSON`: server-only JSON object containing exactly `wallet_address`, `token_address`, `recipient`, `token_decimals`, `gas_limit`, `max_fee_per_gas_wei`, `max_priority_fee_per_gas_wei`. Addresses must be lowercase nonzero EVM addresses; token decimals are integer 2..18; gas limit is integer 21000..1000000; fee caps are decimal strings in wei, positive maximum with priority cap at most maximum. These are explicit operational values, not values selected by a caller or financial-policy confirmation. They do not silently activate a Constitution or a simulation config. Independent executor/signer policy configuration must also agree before execution becomes possible.

No API models, migrations, canonical encoding or money units changed. Runtime assumptions stay unconfigured, expected income stays empty, and the original baseline is $200 short before fees/shocks. Issuance alone does not imply approval or execution. PF-014/PF-015 public execution/reconciliation and PF-016 workflow audit linkage are now integrated; genuine A/B/C proof is indexed in [evidence](../evidence/README.md). New checkouts remain explicitly unconfigured until the operator selects their inputs.

## Validation boundaries

PF-029 tests use a fresh migrated database, real Constitution confirmation, real simulation/policy/Ed25519 code and a read-only RPC transport substitute. Positive tests explicitly stage extra synthetic cash and invented zero-risk assumptions only in temporary test storage; these are not approved runtime finances or live-chain evidence. The baseline denial test restores the original $12,000 assets and reports DENY. A production recomputation callback is exercised by the existing claim guard; a CLAIMED record with no tx hash is not signing, broadcast or execution completion.
