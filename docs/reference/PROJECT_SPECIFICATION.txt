01  Executive specification
ONE-LINE PITCH
ProofFi is an autonomous financial agent that simulates the consequences of a proposed action and independently verifies that the action complies with the user's rules before execution.

The product is built around a simple security premise: an LLM can be useful without being fully trusted. The planner is allowed to reason, recommend, and even fail. It is not allowed to directly authorize or sign a transaction. Authorization belongs to a separate policy and verification layer.
Question
Answer
What is it?
An AI-controlled financial wallet with an independent authorization and verification layer.
What makes it different?
It does not ask only what the AI wants to do; it asks whether the AI should be permitted to do it, under explicit user rules and future-risk assumptions.
Primary user value
Give AI financial autonomy without giving the model unrestricted financial authority.
Competition proof
A real end-to-end flow: natural-language goal -> candidate strategies -> simulation -> verification -> certificate -> approval if needed -> on-chain testnet execution.
Security proof
A malicious or compromised planner can propose an unsafe transfer, but the executor refuses it because no valid certificate can be produced.
MVP positioning
A wallet is the first application. The larger vision is a reusable authorization layer for any AI agent that can move money.

The project must not be pitched as mathematical proof of future safety. Deterministic rules can be verified exactly; uncertain financial outcomes can only be stress-tested or estimated under explicit assumptions. ProofFi therefore uses the term Action Certificate for the combined authorization record.

COMPETITION STRATEGY
The winning version of ProofFi is not the version with the most features. It is the version where one narrow end-to-end workflow is unmistakably real, secure, reproducible, and visually understandable.

03  Problem and product thesis
3.1 The problem
Financial AI is moving from recommendation toward action. An agent can increasingly understand an instruction, decide on a transaction, call a tool, and move value. That creates a mismatch: model intelligence is probabilistic, while financial authorization must be precise.
LLMs can hallucinate, misunderstand instructions, and react inconsistently.
Prompt injection can alter a planner even when the user never intended the resulting action.
"Are you sure?" is not an execution security model; it is a conversational warning.
Static spending limits do not account for obligations, goals, timing, or changing financial context.
An action can be individually reasonable but unacceptable under the user's explicit values or protected obligations.
3.2 Product thesis
DESIGN PRINCIPLE
The system that decides what to do is not the system that decides whether it is allowed to happen.

ProofFi assumes the planner can fail. It protects the execution path anyway. The planner proposes a structured Candidate Action. The trusted verifier evaluates deterministic rules and scenario-based risk thresholds. Only a matching, valid certificate can reach the executor.

06  End-to-end product behavior

Figure 2. The hero workflow from user goal to certified execution.
User submits a high-level financial goal.
Intent parser converts the goal into a structured objective and identifies referenced obligations.
Planner generates candidate strategies; it cannot execute anything.
Time Machine runs named stress scenarios and stochastic simulations for each candidate.
Constitution Engine evaluates deterministic constraints and risk thresholds.
Safe-action optimizer selects the best feasible candidate or searches for the maximum safe amount.
Independent verifier creates an Action Certificate only if every required check passes.
Approval Gate requests explicit human authorization when policy requires it.
Executor independently verifies the certificate, action parameters, state/version freshness, and approval evidence.
Signing service submits the transaction to an EVM testnet.
Audit log links the exact certificate to the resulting transaction hash.

8.3 Monte Carlo prototype model
For the competition MVP, the model should favor transparency over false sophistication. Use configurable distributions and clearly label them as scenario assumptions rather than statistically validated forecasts.
for path in 1..N:    state = current_financial_state    apply(candidate_action)    for each time_step in horizon:        sample asset_return        sample income_delay / income_event        sample emergency_expense        apply scheduled obligations        record liquidity and goal statusmetrics = {  goal_satisfaction_probability,  reserve_breach_probability,  p05_terminal_liquidity,  expected_terminal_value}

Metric
Definition
Goal satisfaction probability
Share of simulated paths in which the protected goal is fully funded by its due date.
Reserve breach probability
Share of paths where liquid funds fall below the Constitution floor at any point.
P05 terminal liquidity
5th-percentile ending liquid balance; an interpretable severe-downside metric.
Expected terminal value
Average ending portfolio value across the declared simulation paths.

CLAIMS DISCIPLINE
Never present "97%" as a real-world probability without context. The UI should say: "97% simulated goal satisfaction under the assumptions shown below."

8.4 Safe-action optimization
The agent should not merely reject an unsafe request. It should search for the best safe alternative. For a monotonic action such as "invest as much as possible," use a bounded search or binary search over the amount, re-running the verifier until the largest compliant amount is found.
objective: maximize investment_amountsubject to:  all_hard_constraints == PASS  simulated_goal_satisfaction >= 0.95  simulated_reserve_breach <= 0.05

09  Proof-carrying financial actions
"Proof-carrying finance" is the product metaphor. Technically, the certificate is a signed verification record, not a mathematical guarantee of future outcomes. It proves what was checked, against which state and policy version, under which simulation assumptions, before execution.

Purpose
certificate_id
Human-friendly immutable identifier, e.g. PF-CERT-002817.
candidate_action

Binds the certificate to the financial state used for verification.
constitution_version
Binds the action to confirmed user policy.

Each rule, PASS/FAIL, and relevant measured value.
simulation_config
Horizon, scenario set, path count, seed, model parameters.
simulation_metrics
Goal satisfaction, reserve risk, downside, expected result.
approval_requirement
Whether human approval is required and why.
issued_at / expires_at
Prevents stale authorization.
nonce
Prevents replay.

Canonical hash of the certificate payload.

Integrity/authenticity signature from the verifier service.
execution_tx_hash
Added after successful execution to close the audit loop.

EXECUTOR INVARIANT
No certificate = no execution. A certificate for $850 cannot authorize $851, a different recipient, a different asset, a stale state snapshot, or a different Constitution version.

11  Component specifications
11.1 Intent Agent
Input: natural-language user goal + current UI context. Output: structured objective, protected references, optimization target, and ambiguity flags. If material ambiguity exists, it must ask the user rather than inventing parameters.
11.2 Planner Agent
Generates a small set of candidate actions. It never decides that an action is compliant and cannot call the signing/execution service directly.
11.3 Time Machine
Evaluates every candidate under named stress scenarios and stochastic paths using a fixed, logged configuration.
11.4 Constitution Engine
Checks hard constraints and threshold constraints against canonical financial state, not natural-language summaries.
11.5 Safe-Action Optimizer
Ranks feasible candidates or searches for the maximum safe amount. It must preserve the user's hard constraints while optimizing the soft goal.
11.6 Independent Verifier
Recomputes required checks and signs the certificate. It must not accept a planner-provided "pass" verdict.
11.7 Approval Gate
Requests explicit approval for new counterparties, transaction classes, or amounts above configured limits. Approval is bound to the exact certificate/action.
11.8 Executor + Signing Service
Validates certificate signature, expiry, nonce, state/policy binding, approval evidence, and exact transaction parameters before signing.
11.9 Audit Service
Stores the full trace and provides the verification/audit UI used in the demo and submission evidence.

13  Security model and threat analysis
SECURITY CLAIM
ProofFi does not claim the entire system remains safe after every component is compromised. The competition threat model assumes the planner/LLM may be malicious or manipulated while the verifier, policy store, approval service, signing service, and executor remain trusted.

Threat
Failure mode
Control
Prompt injection
Planner proposes malicious transfer.
Planner has no signing authority; verifier enforces policy; executor requires a valid certificate.
Parameter substitution
Action is changed after verification.
Certificate hashes exact canonical parameters; executor compares exact action bytes/fields.
Replay
Previously valid certificate reused.
Nonce + expiry + one-time execution status.
Stale financial state
Certificate used after balances/obligations changed.
State snapshot hash/version and freshness window; re-verify on mismatch.
Constitution tampering
Rule set silently weakened.
Confirmed immutable versions; policy changes require explicit user confirmation.
Approval bypass
High-impact action executed without user approval.
Approval token bound to certificate ID/action digest.
Key exposure to LLM
Model leaks or misuses key.
Private key never enters prompts/frontend; isolated signing service only.
Certificate tampering
Displayed certificate differs from verifier output.
Canonical hash + verifier signature.
Simulation gaming
Planner chooses assumptions to make action appear safe.
Simulation configuration is policy/system-controlled, logged, and visible to the user.
Backend direct-call attack
Attacker calls executor endpoint directly.
Executor independently verifies certificate/approval; UI is not the security boundary.
Unsupported asset/recipient
Planner tries unapproved instrument or address.
Allowlist/counterparty policies in deterministic engine.
Availability failure
Simulation/verifier unavailable.
Fail closed: no certificate, no financial execution.

13.1 Red-team requirement
The demo should intentionally allow the planner to be influenced by a malicious instruction. That is stronger than showing an LLM that simply refuses the attack. The planner should produce the dangerous candidate action, and the trusted path should block it.
malicious_input -> planner proposes transfer(4000, 0xBAD...)verifier:  FAIL unknown recipient  FAIL autonomous amount limit  FAIL protected tuition balance  FAIL simulated goal thresholdexecutor -> 403 INVALID_CERTIFICATE / no transaction signed

14  On-chain execution design
Use an EVM testnet and synthetic/test tokens only.
Support one or two transaction types maximum: token transfer and/or a simple swap/rebalance if stable enough.
The private key lives only in the backend signing service environment.
Executor receives a validated action object, not free-form planner text.
After submission, store tx_hash on the Action Certificate/audit record.
Optional stretch goal: anchor certificate_hash on-chain or in transaction metadata/events if implementation remains simple and reliable.
The goal is not to build a DeFi protocol. The chain is the final execution and evidence layer. The product story remains authorization infrastructure for autonomous finance.

18  Judging strategy
Judge question
ProofFi answer
Is this just a chatbot?
No. The task finishes in a real testnet transaction, with independent backend enforcement and an audit trail.
Is this just a spending limit?
No. Authorization depends on the user's full obligations, future-risk scenarios, and explicit policy, not just transaction size.
Is the simulation a fake prediction?
No claim of prediction. Assumptions, stress scenarios, path count, seed, and metrics are visible and reproducible.
What if the AI is compromised?
The planner may fail. It still cannot sign; the verifier and executor enforce independent policy.
Why blockchain?
It provides verifiable execution evidence for Topic F. The product is not defined by crypto; it is an authorization layer.
What is the innovation?
Proof-carrying financial actions: deterministic user policy + future-risk analysis + certificate-gated execution.
What scales beyond the demo?
Any AI agent that can move value could submit actions to a ProofFi verification API before execution.

MEMORABLE LANGUAGE
Primary line: "ProofFi separates financial intelligence from financial authority." Secondary line: "We do not need to assume the AI never fails; we prevent AI failure from automatically becoming financial execution."
